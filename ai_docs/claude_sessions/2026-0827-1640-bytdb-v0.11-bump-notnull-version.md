# Session: bytdb v0.6.4 → v0.11.0, and `notes.version` becomes NOT NULL

**Session ID:** `91f14e74-5f6f-44c1-98b2-040145d0df9c`
**Date:** 2026-08-27
**Branch:** master
**Base commit:** `ef40649` — Show the web UI that a summarize is running

## Context

GoNotes would not start. Every entry point died in the same place:

```
ERRO adding a column with DEFAULT to a non-empty table is not supported
  column="version"  table="notes"
  main.runTui -> models.openDatabases -> models.(*dbEngine).ensureColumn
    -> bytdb.(*Engine).AddColumn   (bytdb@v0.6.4/ddl.go:206)
```

The `version` column added in the optimistic-concurrency work
(`models/schema.go`) is declared `BIGINT DEFAULT 1`, and bytdb v0.6.4 refused
`ADD COLUMN ... DEFAULT` on a table that already had rows. Not a GoNotes bug —
a guard upstream that had since been lifted. The user had already fixed it on
the bytdb side and arrived with the answer: bump the pin.

The session ran in two passes, because bytdb released twice while we worked.

## Pass 1 — v0.6.4 → v0.10.0

`go get github.com/rohanthewiz/bytdb@v0.10.0` (which also pulled btypedb
v0.6.2 → v0.7.0). Build and full suite green with no source changes.

What v0.10.0 changed, from its own session log
(`ai_docs/claude_sessions/2026-0827-1518-add-column-default-backfill.md` inside
the module):

- `AddColumn` now evaluates the DEFAULT once and writes it into every stored
  row, **inside the same transaction that publishes the descriptor**. Rows and
  schema commit together or not at all.
- So `NOT NULL DEFAULT x` became legal on a non-empty table. `NOT NULL` alone
  still requires an empty one; `DEFAULT NULL` skips the rewrite.
- Cost moves from O(1) to O(rows), but only when a default is present.

## Pass 2 — v0.10.0 → v0.11.0

Purely additive over v0.10.0: `ALTER TABLE … ALTER COLUMN c SET NOT NULL` and
`DROP NOT NULL`. Nothing in GoNotes broke. The diff worth knowing about:

- `Engine.SetColumnNotNull` validates by scanning stored **value tuples** for
  the column's tag rather than materializing rows — a NULL column is simply
  omitted from a row's value, so presence of the pair *is* "not NULL". Read-only,
  no rewrite, and it publishes the flag in the same transaction as the scan.
- A NULL found → the statement fails with Postgres's wording (SQLSTATE 23502).
- `SetColumnNotNull` on an already-set column is a no-op (returns `nil, nil`
  from the closure, so `alterDesc` skips the descriptor write) — idempotent,
  which is what makes it safe on a startup path.

## Adjustments made (`models/schema.go`)

### 1. A comment that had become false

`ensureColumn`'s docs asserted that bytdb "cannot retroactively apply" a DEFAULT
to rows already on disk, which is why `backfillSQL` existed. True at v0.6.4,
false from v0.10.0. Rewritten to say what the engine now does, and to reframe
`backfillSQL` as the belt to the ALTER's braces — still worth passing for a
column whose NULLs are dangerous rather than untidy, since it covers the two
cases the engine's backfill cannot: a column added by some other path, and rows
that acquire a NULL *after* the migration.

### 2. New `ensureNotNull` helper

```go
func (en *dbEngine) ensureNotNull(table, column string) error
```

Skips a column that does not exist (mirroring `ensureColumn`'s tolerance), then
issues `ALTER TABLE … ALTER COLUMN … SET NOT NULL`. Idempotent by virtue of the
engine's own no-op. A column still holding NULLs fails startup loudly, which is
the correct direction — better than a constraint quietly not being what the
schema claims. Callers therefore run any backfill first.

Its reason for existing: without it, a database that reached a column through
`ensureColumn` keeps the nullable version **forever**, and only brand-new
databases would ever exercise the strict path. The two ages diverge permanently.

### 3. `notes.version` hardened to NOT NULL

The hazard was already named in the existing comment: a NULL `version` reads
back as 0, which the stale-write guard treats as "unchecked", so a note could
silently opt itself out of the optimistic-concurrency protection the column
exists to provide. That is now a constraint instead of a hope.

Three database ages converge on the same shape, and the code says so:

| database age | gets NOT NULL from |
|---|---|
| created from scratch | the `CREATE TABLE` (`version BIGINT NOT NULL DEFAULT 1`) |
| predates the column | the ALTER — `BIGINT NOT NULL DEFAULT 1`, rows backfilled in the same transaction, so the constraint is satisfiable the moment it is published |
| took the earlier *nullable* form of this migration | `ensureNotNull`, after the `UPDATE … WHERE version IS NULL` has cleared anything left behind |

## Notes for next time

- **bytdb is single-process.** Every check above ran either against a copy or
  with the server confirmed down. That is not optional.
- `gofmt -l models/` flags `category.go` and `store.go`. Pre-existing — verified
  by stashing — and deliberately left alone.
- Still absent upstream, if they are ever wanted: `ALTER COLUMN TYPE`, and
  `ADD COLUMN` with an identity column (existing rows would need drawn values).
- The engine's DEFAULT backfill only understands the literal vocabulary
  `sql/parser.go`'s `renderLit` can emit — `null`, bools, ints, floats, quoted
  strings, `now()`, `current_date`. An expression or a cast in a DEFAULT fails
  the ALTER rather than leaving old rows NULL. Worth knowing before adding a
  column defaulted to something clever.
