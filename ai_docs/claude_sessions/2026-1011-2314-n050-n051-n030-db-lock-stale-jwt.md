## N-050: two processes on one database (`fb0732c`)

bytdb went from v0.11.0 to v0.21.2, and btypedb from v0.7.0 to v0.9.0. The
full suite was green right after the bump, with no API breaks across the ten
releases. Every open engine now holds an exclusive, non-blocking flock on a
`<db>.lock` sidecar. A second `Open` fails with `bytdb.ErrLocked`
(= `btypedb.ErrLocked`).

- **`models/db.go`.** Adds `IsDBLocked(err)` (an `errors.Is` on
  `bytdb.ErrLocked`, so callers don't import bytdb) and `LockedMessage`,
  which `openDatabases` wraps a lock failure in. If the private open fails
  after the public one succeeded, the public engine is now closed, so a
  failed open leaves no lock behind. The new test catches this.
- **`main.go`.** `serr`'s `Error()` is the root error by design, so the
  friendly wrap only showed up in `fields.msg`. `main` now prints
  `gonotes: <LockedMessage>` to stderr ahead of the structured log line when
  `IsDBLocked(err)`. `runTui`'s server fallback now fires only on
  `up && IsDBLocked(err)`. A corrupt WAL or a bad key is reported rather
  than redirected to another directory's notes. `--local` names the lock
  when that's the cause.
- **`account_cmd.go`.** The health probe stays, because it names the
  server's URL, and its comment now says the lock is the guarantee behind
  it. A lock failure adds "stop the server using <dir>". Decision: keep the
  probe for its friendlier message, as the item suggested.
- **Docs.** The README's three "single-writer" passages now say the rule is
  enforced and that a leftover `.lock` file is harmless. The gonotes
  skill's "bytdb takes no OS file lock" claims and the
  `models/account_admin.go` comment were corrected. `.gitignore` gains
  `*.bytdb.lock`.
- **Checks.** New `models/db_lock_test.go`: a held public DB makes
  `InitTestDB` fail with `IsDBLocked` and the message. A held private DB
  releases the public one, and the pair reopens once the holder closes. A
  scratch server on :18471 ran against a scratchpad dir (the first attempt
  died on a short JWT secret, which looked like the lock failing until I
  read the log). With it running, `account list`, `export-md` and
  `tui --local` were all refused, naming the holder PID.
- **Not driven end to end.** The `runTui` fallback (a server on 8444
  serving a different dir while these files are held) wasn't exercised.
  Port 8444 here is the user's live server, and pointing a TUI at it would
  open their notes.
- **Caveat.** The lock only protects processes built on the new bytdb. A
  server or MacApp built before this commit takes no lock, so a new CLI
  beside an old app is still unguarded until the app is rebuilt.

## N-051: JWT trusted a GUID without a lookup (`5af169e`)

`JWTAuthMiddleware` now calls `currentUserForToken` after
`ValidateToken`. That's a `GetUserByGUID` (guid is UNIQUE, and bytdb holds
it in RAM). A GUID no account holds, or a disabled account (the rule Login
and Refresh already apply), is unauthenticated, so `RequireAuth` returns
401. Username and admin now come from the record rather than the claims.
A lookup error fails closed and is logged.

- **No cache, on purpose.** The in-server hub-identity reconcile
  (`AlignLocalUserWithHub`) would have to invalidate it, and an entry that
  outlives its account is the same gap again. `account merge` can't run
  beside the server now that N-050's lock exists, so a restart already
  clears any in-process state.
- **Clients.** The web UI's `app.js` clears the token and goes to `/login`
  on a 401. The TUI's HTTP store does one silent re-login with the
  remembered credentials, which succeeds after a reconcile (same username,
  new GUID) and fails cleanly after a merge.
- **Checks.** New `web/api/auth_stale_guid_test.go`. After
  `MergeLocalUsers`, the old token gets 401 on GET and POST `/notes`;
  against the stashed old middleware it got 200 with an empty list and
  400. Logging in as the survivor works, and a rename keeps the session.
