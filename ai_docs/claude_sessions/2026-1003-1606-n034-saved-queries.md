## Shape of it

```
web query bar ──POST /query/saved, /query/history──┐
TUI query screen ──store.RecordQuery (local|HTTP)──┤
                                                   ▼
                                   saved_queries (PRIVATE DB)
                                                   │
             models.CompleteQuery on an empty box ◀┘  → both UIs render it
```

- **Note-link completion.** `guid = ` gets a value case in
  `valueSuggestions`. It offers the user's notes most-recent first. A note
  matches on its title, a GUID prefix, or a `[[note:GUID|…]]` link pasted
  inside the quotes. The label is the title; accepting inserts the quoted
  GUID. This is the same title lookup the link picker does, run by the
  server's completer.
- **Saved and recent queries come through the completer.** They are not a
  separate list in each UI. With nothing typed, `CompleteQuery` puts saved
  rows (kind `saved`), then history (`history`), ahead of the examples. A
  partial first word offers saved queries whose *name* matches. Past the first
  token they never appear. A history row whose text equals a saved query is
  dropped. `QuerySuggestion` gained an `id` so a UI can forget a row straight
  from the popup.
- **Storage.** `models/saved_query.go` plus a `saved_queries` table
  (`kind` saved|history, `name`, `query`, timestamps).
  - Saving upserts by name, ignoring case; the new spelling wins.
  - A save must parse, and a failure comes back as the usual positioned
    `*QueryError`.
  - History dedupes (a repeat moves to the top) and is pruned to 25 per user.
  - Writes are serialized by a package mutex because they read, then write.
  - Validation failures are a `*SavedQueryInputError`, so the API answers them
    400 and storage failures 500.
- **API** (`web/api/saved_queries.go`): `GET/POST /api/v1/notes/query/saved`,
  `DELETE /api/v1/notes/query/saved/:id`, `POST /api/v1/notes/query/history`.
  They are registered ahead of `/notes/:id`.
- **Web** (`advanced_search.js` v2, `advanced_search.go`, `app.css` v16):
  - Saving: a ☆ button and ⌘S/Ctrl+S open an inline name row. The name is
    prefilled when the text is already a saved query.
  - Forgetting: `Shift+Delete` on the highlighted row, or a hover ×.
  - Recording: each deliberate run is posted to history, fire-and-forget.
  - `authedFetch` now takes a method and body, and reports a network failure
    as status 0 instead of throwing.
- **TUI.**
  - `Store.RecordQuery` is a new seam method, implemented in local, HTTP and
    fake stores.
  - `runAndRecordQueryCmd` is used only by the query screen's Enter.
  - The browse screen's refresh keeps using `runQueryCmd`, which does not
    record.
  - Saved and history rows are whole-query kinds (`isWholeQueryKind`), with
    the same glyphs as the web (☆ ↺).

## Decisions worth remembering

- **The private DB, not the public one.** Every other per-user system table
  lives in the public DB. Query text is content, though: `title = 'Secret
  plan'` quotes the very notes it finds. The private DB is the one that gets
  encrypted, so the table lives there. It is created by a new
  `createPrivateOnlySchema`. `TestSavedQueriesLiveInThePrivateDatabase` pins
  this.
- **Not synced.** A saved query belongs to the server you query against. Web
  and TUI-in-HTTP-mode already share it. Syncing it would need a second
  change-tracking scheme for a convenience nobody asked to roam.
- **History is recorded by an explicit POST**, not as a side effect of
  `GET /notes/query`. The TUI re-runs an active query through that endpoint on
  every reload, and only the client knows a refresh from a run.
- **One-time `localStorage` migration.** On the bar's first open (when the
  user is certainly signed in), the old list is posted oldest-first, which
  keeps its order. It is removed only after every POST succeeds; a 401 leaves
  it for next time.

## Bugs found along the way

- **My own test assumption was wrong.** 30 runs against a cap of 25 keep
  `id = 5`…`id = 29`. Re-running an existing entry adds no row, so it prunes
  nothing. Fixed the test, not the code.
- **The first `SaveQuery` handler mapped every error to 400 and logged it.**
  It was replaced with the typed `SavedQueryInputError` split.
- **Not a bug:** `title = AND` parses (the bare word is a value), so saving it
  succeeds. A truly malformed query (`category = `) is refused with the range
  selected.
